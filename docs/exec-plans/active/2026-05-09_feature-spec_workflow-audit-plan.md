## 用户问题
在当前治理升级阶段完成后，还缺一份独立的后续计划来系统性检查重复文档、职责重叠 / 模糊和 token 浪费来源。

## 期望结果
新增一份独立执行计划，把上述三类问题作为下一个治理阶段的主目标，并明确发现、分类、验证和后续修复路由。

## 范围
- 审计入口文档、索引文档、模板、prompt、skills 之间的重复与边界问题。
- 识别高频重复说明、双重真相来源和无效上下文消耗。
- 定义发现问题后的后续治理策略与拆分原则。

## 非范围
- 直接大规模改写受影响文档。
- 重新讨论已定稿的 Phase 4 澄清 / handoff / hooks 基线。
- 把所有未来治理主题一次性塞入同一份计划。

## 约束与禁止
- 必须先完成审计计划，再决定修复优先级。
- 不得把“审计计划”写成“直接实施清单”。
- 不得忽略 token 成本与收益说明。

## 用户流程
维护者完成当前 Phase 4 收口后，打开新的审计计划，按计划分阶段检查文档与工作流中的重复、边界模糊与 token 成本，并为后续修复提供统一入口。

## 边界情况
- 某些看似重复的内容实际承担不同生命周期职责。
- 某些 token 成本来自必要安全门，不应被简单视为浪费。
- 某些重复内容已经在旧计划或 observation card 中记录，需避免二次计划化。

## 风险
- 审计范围过宽导致再次变成混合目标计划。
- 只记录问题、不定义验证方式，导致后续难以落地。

## 验收标准
- 计划内明确三类核心问题及其验证方法。
- 计划对“哪些问题先观察、哪些问题可直接治理”有明确分流。
- 计划与现有治理升级计划之间不存在职责冲突。

## 成功指标
- 新计划能作为下一轮治理的单一入口。
- 后续审计发现的问题不再回写到当前 Phase 4 活动计划里。
