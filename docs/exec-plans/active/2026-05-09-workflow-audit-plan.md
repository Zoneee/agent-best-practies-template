# 执行计划

## 标题
工作流检查计划：重复文档、职责边界与 token 成本审计

## 状态
草稿

## 阶段完成度概览
- Phase 1：待开始，先完成问题清单与审计样本面收敛。
- Phase 2：待开始，执行重复文档与职责边界审计。
- Phase 3：待开始，执行 token 成本与上下文噪音审计。
- Phase 4：待开始，整理治理建议、验证证据与后续计划拆分。

## 交付目标与成功标准
- 系统识别模板仓库中重复文档问题、职责重叠 / 模糊问题和 token 浪费问题。
- 把问题分类为“可直接治理”“需长期观察”“需单独立项”三类，避免再次混合目标。
- 为后续治理产出可执行的优先级、验证方式与证据记录入口，而不是只留抽象抱怨。

## 范围
- `AGENTS.md`、`docs/` 索引、`templates/`、`.github/prompts/`、`.github/hooks/`、`skills/` 与根目录速查文件之间的职责和信息分布。
- 重复说明、双重真相来源、同义改写但无新信息的噪音段落。
- 会显著增加默认上下文或执行上下文长度的文档与规则组织问题。

## 非范围
- 本计划不直接实施大规模文档重写。
- 本计划不重新设计已稳定的 Phase 4 澄清 / handoff / hooks 基线。
- 本计划不把运行时 hooks bug 修复再次并入同一计划。

## 质量门禁
- 每一类问题都必须给出“为什么是问题”和“为什么值得治理”的 token / 维护成本解释。
- 发现重复或重叠时，必须区分“真实冲突”与“生命周期分层导致的必要重复”。
- 输出必须包含验证与证据记录方式，不能只列问题清单。
- 后续治理建议必须能拆为小范围 PR，不混合多类目标。

## 验证计划
1. 审计样本验证：选取代表性入口、模板、prompt、索引文件作为样本面，确认覆盖核心工作流。
2. 重复问题验证：对候选重复段落做源头 / 下游对照，确认是否存在双重真相来源。
3. 职责边界验证：对疑似重叠文档明确其触发场景、使用时机和唯一职责。
4. Token 成本验证：基于默认阅读链路与高频执行链路，识别长期常驻上下文中的低收益内容。
5. 建议可执行性验证：检查后续治理建议是否可拆分为独立计划、PR 或 observation card。

## 证据记录方式
- 在本计划的 `进展日志` 中记录样本面、已确认问题类别与验证结果。
- 对长周期观察项，使用 `templates/observation-record-template.md` 记录 observation card，再把稳定结论回写本计划。
- 对后续拟实施的治理项，只在本计划记录问题摘要与入口计划路径，不直接写实施细节。

## 文档更新与治理
- 受影响文档：`AGENTS.md`、`docs/index.md`、`docs/standards/index.md`、`templates/`、`.github/prompts/`、`skills/` 及后续审计中识别出的高频入口文件。
- 是否需要同步修订或移除过时内容：需要，在进入实施阶段时按审计结论执行。
- 本计划的验证证据将记录在：本计划 `进展日志`、必要 observation card、后续治理计划。

## 风险
- 审计范围过宽，重新变成大杂烩计划。
- 把必要的生命周期分层误判为重复。
- 只记录问题不定义验证方式，导致后续无法执行。

## 回滚与止损
- 若审计范围膨胀，先缩回代表性样本面，再决定是否拆出多个子计划。
- 若某类问题无法形成稳定判断，降级为 observation card，而不是强行写入治理结论。
- 若审计本身引入更多文档噪音，应先收敛计划结构，再继续扩写问题清单。

## 背景
当前治理升级计划已经完成 repo-local 澄清、交接、hooks 基线与最小 `.github/hooks` 草案的收敛。下一轮工作不再适合继续堆叠在原计划里，而需要独立审计重复文档、职责重叠 / 模糊和 token 成本来源。

## 问题摘要
- 仓库仍可能存在生命周期不同但表述相近的文档，需要区分必要分层与无效重复。
- 部分入口、模板、prompt 与技能说明在职责边界上仍可能存在模糊地带。
- 默认阅读链路、计划链路和执行链路中的低收益说明可能持续抬高 token 成本。

## 约束与禁止
- 本计划只负责审计与后续治理排序，不直接混入批量修复。
- 每个问题结论都要附带证据或最小可重复判断依据。
- 不得把已在 Phase 4 稳定的结论重新打开为无边界争论。

## 实现步骤

### Phase 1：审计样本面与问题分类基线
1. 选取代表性入口、模板、prompt、skills、hooks 与索引文件作为样本面。
2. 定义三类问题的最小判断标准：重复文档、职责重叠 / 模糊、token 浪费。
3. 明确哪些现象属于必要分层，哪些属于治理对象。

### Phase 2：重复文档与职责边界审计
1. 检查高频入口与高频模板中的重复说明。
2. 对疑似重叠的文档给出唯一职责、触发场景与是否保留。
3. 形成“可直接治理 / 需观察 / 需另立计划”分类。

### Phase 3：token 成本与上下文噪音审计
1. 沿默认阅读链路与高频执行链路检查长期常驻上下文。
2. 识别低收益、重复、无直接执行价值的说明。
3. 给出压缩建议与风险说明。

### Phase 4：治理建议与后续拆分
1. 汇总审计结论与证据。
2. 按问题类型拆分后续治理计划、observation card 或小 PR 建议。
3. 回写与当前治理升级计划的边界，避免双重真相来源。
