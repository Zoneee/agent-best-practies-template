# delivery-quality-first

## 目的
无论处于 Plan、Agent 还是 Ask 模式，先把"为什么要这样做、如何保证安全交付、如何验证、如何控制风险"说清楚，再讨论具体修什么或怎么做。

过程控制优先于模板填空；章节数量不能替代解释质量。

## 适用范围
- 制定或审阅执行计划
- 提供方案建议或技术咨询
- 执行实现任务
- 评审或复盘交付质量

## 默认质量契约
- 每份输出至少回答 3 件事：目标是什么、为什么这样安排、下一步具体做什么。
- 质量信息必须存在，但按任务层级压缩表达；不要为了过 gate 把章节写满却不解释目标和取舍。
- 若前几行仍不能让读者看懂目标和理由，或步骤仍停留在 Phase 标题、抽象动词和不可直接接手的粒度，视为输出不合格。

## 分层输出要求

### Ask / chat-light
- 默认使用轻量结构，先给判断、理由和下一步。
- 适用边界、验证和风险按需补充，不默认展开为完整治理清单。

### Plan / plan-light
- 先说明目标与理由，再写范围、细步骤和验证。
- 每个步骤至少包含：本步目标、依赖、动作、验证。
- 只有多阶段、高风险或跨轮执行时，才升级为完整治理结构。

### Agent / full-governance
- 开始执行前，明确当前采用的范围、验证路径、证据要求和主要风险。
- 在高风险执行中，允许展开完整门禁，但仍要让读者先看懂目标和为什么这样安排。

## Plan 模式要求
- 计划必须先说明目标与理由，再写如何保证交付质量和问题修复方案。
- 必须显式列出验证计划、证据要求、风险与回滚策略。
- 步骤必须细到可直接执行；不接受只有 Phase 标题或抽象动词的计划。
- 若无法定义验证方式，不得将计划从草稿状态进入“执行中”或开始实施。

## Agent 模式要求
- 开始执行前，先声明本次采用的质量门禁、验证路径和本轮切片目标。
- 不得跳过范围控制与证据设计直接开始改动。
- 若信息不足，先补计划、文档或约束，再继续执行。

## Ask 模式要求
- 不得只回答"推荐做什么"，必须同时回答"为什么这样做"以及"为什么这样做可以被验证"。
- 必须说明建议的适用边界、主要风险和下一步动作。
- 若证据不足，应优先暴露不确定性，而不是给出过度确定的结论。

## 自检问题
- 我是否在前几行就让读者看懂了目标和理由？
- 我是否按当前任务层级选择了轻量还是完整结构，而不是默认重写整套模板？
- 我是否写清楚了验证方式与证据来源？
- 我是否说明了主要风险、边界与止损方式？
- 我的步骤是否细到可以直接执行或交接？
