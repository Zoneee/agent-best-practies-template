# Skill：先计划，后编码

## 目的
在实现前形成可执行计划，防止失控改动，也防止只有方向没有路径。

## 适用场景
- 任何预计超过 15 分钟的任务
- 涉及多个文件或模块的改动
- 涉及 Schema、API、迁移、认证、基础设施或 UI 行为的工作
- 没有明显根因的 bug 修复

## 所需输入
- 任务描述
- 澄清契约，以及受影响的用户流程、feature spec 或 bug 报告
- 相关产品规格
- 相关架构文档
- 相关开发规范

## 执行步骤
1. 用 3-5 条要点总结问题，并补一句“为什么值得现在处理”。
2. 识别可能受影响的模块、文件和边界。
3. 判断当前工作适合内联轻量计划，还是需要落盘到 `docs/exec-plans/active/` 的完整执行计划。
4. 识别约束和禁止区域。
5. 定义验收标准。
6. 定义验证步骤。
7. 把执行步骤拆到可直接接手的粒度；每一步至少写明本步目标、依赖、动作、验证。
8. 记录风险与未知项。
9. 较大的工作保存计划至 `docs/exec-plans/active/`，较小的工作在 PR/任务中内联记录。
10. 若执行将跨多轮对话、启用 Autopilot、或需要显式的 stop condition 与验证门禁，再基于稳定计划补充 `plan -> execute handoff contract`。

## 输出格式
- 目标与理由
- 问题描述
- 范围
- 受影响区域
- 执行步骤（单一产出 / 依赖 / 动作 / 验证）
- 验收标准
- 验证计划
- 风险
- 后续事项
